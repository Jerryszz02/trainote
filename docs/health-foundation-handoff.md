Value types are Codable, Equatable, and Sendable. Computation schema starts at 1 and is independent of persistence 1.2 / backup 2.
- `AnalysisFixtures` provides deterministic synthetic complete training/diet, missing HRV, manual-only, unknown movement, declined AI, overnight sleep, and duplicate-source scenarios. Fixture calculators/report generators are explicitly synthetic; production assembly does not install them.
- `HealthFoundation` is injected into the existing app environment. It exposes `repository`, optional `consent` / `healthData`, and `setupFailure`. Optional subsystem setup failure keeps original local recording available. No authorization prompt occurs on construction. Foreground resume synchronizes only after the separate health connection consent exists.
- `SwiftDataAnalysisRepository` writes in isolated transactions and returns values. `currentManualTargets` exposes the existing `NutritionGoal` without fabricating historical revisions. `goalHistory` contains only explicitly recorded revisions. `appendGoalRevision` only imports/appends immutable historical facts. Completeness uses a full food-log revision digest; editing a meal invalidates confirmation. B/F should call `AnalysisFingerprint.foodLogs` for the exact recorded day and timezone when confirming.

## Atomic target application for B/F

The additive contract is in `GoalRevisionValues.swift`; existing DTO fields and persistence schema are unchanged. `AnalysisRepository` now exposes:

```swift
func goalRevisionState() throws -> GoalRevisionState
func applyGoalRevision(_ request: ApplyGoalRevisionRequest) throws -> GoalRevisionApplicationResult
```

- `ApplyGoalRevisionRequest` contains `revision: NutritionGoalRevisionValue` and `expectedState: GoalRevisionState`. Obtain expected state from the repository before proposing/confirming an action. State includes `currentGoal` (ID, targets, updatedAt), `latestRevisionID`, and a deterministic `historyFingerprint`.
- One isolated SwiftData save checks that state, retains the existing current-goal UUID, updates its targets/time, and appends immutable history. On first adoption with an old current goal, it also creates a manual baseline: `effectiveAt` is the old `NutritionGoal.updatedAt`; `createdAt` is the application request's creation time. An unset previous goal has no invented baseline. An explicit first application can establish a target; absence alone never establishes one.
- Result fields are `state`, `appliedRevisionID`, `insertedBaselineRevisionID`, and `wasAlreadyApplied`. Exact revision-ID/content replay returns the current state without reapplying a superseded or undone target. Reusing a proposal with a different ID is explicitly rejected.
- Undo uses a new manual revision with `reversesRevisionID` set to the current latest non-reversal revision and targets exactly equal to its predecessor. It restores those targets and appends the undo in the same save. A missing predecessor, arbitrary replacement values, an already reversed action, or an older superseded action cannot be undone by this API.
- `createdAt` must be the new application's actual timestamp and later than the prior current/revision timestamp. No future scheduled application or backdated effective target is silently applied. Initial adoption must take effect after the old current target's update time; subsequent effective dates cannot precede the last revision's effective date.
- `GoalRevisionConflict` distinguishes `staleState`, `revisionIDConflict`, `duplicateProposal`, `alreadyReversed`, `invalidReversal`, `invalidChronology`, `inconsistentHistory`, and `ambiguousCurrentGoal`. On stale state, reload and re-confirm instead of overwriting. Existing Settings/manual-target writes must also route through this API once history exists; unrecorded changes to the legacy target are detected rather than used as an invented history predecessor.
- The transaction rolls back both current and historical records if save fails. This API does not calculate a proposal, change preference modes, or perform network/UI work.
- Backup preflight treats current targets plus history as a coupled state: conflicting shared goal/revision IDs or incompatible active targets are rejected before any import write. Equal archive values compare at the existing ISO-8601 backup precision so an unchanged backup remains idempotent. It never silently overwrites the destination target to accommodate incoming history.

## Health reads and local storage

- The production client requests only body mass, sleep, resting heart rate, HRV SDNN, steps, active energy, and workouts, with **no write types**. `NSHealthShareUsageDescription`, HealthKit entitlement, and background-delivery entitlement are configured in `project.yml` / `Trainote.entitlements`.
- Observer callbacks trigger anchored queries. A single atomic file transaction contains samples, deletions, read status, and the new anchor. UUID repeats/deletions are idempotent. Failed writes leave the previous anchor and data intact. Observer completion follows the transaction attempt; foreground refresh retries failures. Disconnect cancels observers and in-flight read queries and prevents late results repopulating cache.
- `HealthLocal/cache.json` and `consent.json` are excluded from system backup and use complete-until-first-authentication file protection. Health samples/anchors are never stored in the main ModelContainer or the user JSON archive. The cache retains at most 90 days; its anchored-query start predicate remains fixed until a clear/reconnect. This is a product retention limit, not a medical parameter.
- Authorization request completion is not a grant of all read permissions. `unknown`, `samplesAvailable`, `noSamples`, `failed`, `disconnected`, and `unavailable` describe observations/app state. Empty results never become “permission denied.” Cached availability does not prove current system read access.
- Sleep excludes in-bed/awake, unions overlaps within a chosen source, and chooses one priority source per night. A night is noon-to-noon, labelled by the ending day. Intervals are clipped to the query window and split at local noon before source selection/union, using calendar boundaries across daylight-saving transitions. HRV remains separated by definition/source/product/context; unspecified context stays unspecified. Fresh activity totals use per-source HealthKit daily statistics, choosing a preferred/deterministic source instead of summing devices. Local cached activity is marked estimated; quantities are apportioned at their original density after query-window and local-midnight splitting, before source selection and overlap deduplication. External workouts expose only time, activity code, provenance, and possible duplicate IDs; they never imply local exercise sets.

## Consent and report integration for E/F

- `LocalConsentStore` independently records `.healthData` and `.aiReports`, their versions, grant/revocation dates, and in-process generation leases. Backups cannot restore either consent. The constants `health-read-v1` and `ai-report-v1` identify the initial local explanations; E/F must change the AI version and obtain consent if its real disclosure scope changes.
- F must update Settings/onboarding backup wording to explain v1/v2 compatibility and the health/consent/report exclusions; existing Settings navigation and text remain under F ownership.
- F's health connect action calls `requestReadAuthorization()`. Explicit disconnect calls **`healthData.disconnectAndDelete()`**, not only `consent.revoke(.healthData)`, so cache/anchors and dependent derived stores are deleted together. A failure is surfaced for retry. Manual records stay intact.
- E registers its real derived report/snapshot store through `healthData.addDerivedDataInvalidator`. That store implements `HealthDerivedDataInvalidating.deleteHealthDependentData()`. A only supplies this hook because E owns the actual report cache. F/E must register before any report is cached.
- E registers `consent.onRevocation(.aiReports)` to cancel pending requests/retries and separately revokes server consent. Local AI revocation does not delete health data or automatically delete historical AI reports. E owns the independent “delete AI reports” action and server semantics.
- `ReportSnapshotBuilder.prepare` first requires a valid AI consent lease, freshly queries the entire requested health window in the analysis timezone, reruns injected calculators/candidates, and resolves transitive fact dependencies. Missing or no-longer-readable raw health dependencies are rejected. It never uses old anchored cache or accepts cached calculator results as a substitute. Inferred baselines must carry transitive dependencies. Missing health data can still produce a manual-only report.
- `validateBeforeSending` checks both leases immediately before send/retry. Each **new report** requires a new `prepare`; never reuse a prepared snapshot for a later new report. Revocation during preparation invalidates it. External system revocation after a completed read is not instantly observable; the UI must retain explicit disconnect.
- Only `ReportInput` is intended for the report transport. It has no profile names, contact details, notes, exact locations, or raw heart-rate arrays. E must apply its own size/output/schema checks and may omit local-only dependency metadata from the wire after local validation. This foundation performs no AI network calls.
